# 203-CLI: rules for changing it

This repository is public and is the one source of `203cli` and the 203-community Agent Skill. People install it from
npm, the package `203cli` (`npm install -g 203cli`, then `203cli skill install`), published by `.github/workflows/release.yml`
when a tag `vX.Y.Z` equal to `package.json`'s version is pushed (npm trusted publishing: no token; the files in
`package.json` `files`). Advertise only that. The 203 community also packs a pinned commit as the skill its
`install.sh` installs (kept working for scripts that have it, CI among them): it reaches those when the community pins
the new commit.

203cli is the only name (the user, 2026-11-22: "只保留203cli"; the community refuses any other). Nothing here runs,
answers to, falls back to or mentions an earlier name: no other command, script path, npm package, environment variable
or config folder. Do not add one back.

## What 203cli promises (keep it)

- One dependency, optional and for Windows' COM ports only: `@serialport/bindings-cpp`, pinned (prebuilt N-API binaries;
  its install step only picks the prebuilt one), imported by `flash` on Windows alone (decided 2026-11-23: Node has no
  serial port API there). Nothing else may depend on it, and without it everything works but `flash` on Windows
  (`serial_missing`). No other dependency, no install scripts of 203cli's own, Node 18 or later, macOS, Linux and
  Windows (on Windows everything but `log`; `board`, and `flash` restarting a running firmware, through python's
  hidapi); CI tests all three. No build step.
- With `--json` every answer is JSON on stdout and an error is one JSON line on stderr, its last line, with
  `error`, `code`, `hint`, `exit` and `next` (commands ready to run; never `--force` / `--yes` from a guess). The exit
  codes are the table in `scripts/guide.mjs` (`EXIT_TEXT`) and `SKILL.md`. Commands, flags, error codes and help
  topics are an interface agents rely on: add, do not rename or remove.
- Re-runs change nothing (`already_published`, `already_deleted`), `--dry-run` checks what the server will check.
- Never print a token; never ask for one in a chat. The one exception: `admin bots create` and `admin bots rotate` without
  `--token-file` print the new bot token once, because the admin asked for it (the user, 2026-11-23); `--token-file` writes it
  to a file (mode 600) and prints only the path.

## Files

- `scripts/commands.mjs` is the command table: `--help`, `--help --json` and `reference/cli.md` come from it.
  After changing a command, a flag or an error code: `npm run reference` (`node scripts/203cli.mjs help --reference >
  reference/cli.md`); the tests fail while it is stale. Raise `CLI_VERSION` (`scripts/lib.mjs`) and `package.json`'s
  `version` together.
- `scripts/launcher-usb.mjs` and `scripts/recover-plan.mjs` are also the community website's own modules (it serves
  them as `launcher-usb.js` and `recover-plan.js`): keep them plain ES modules that run in a browser and in Node.
- `reference/api.md` is generated by the community from its API's route table; take it from there, do not edit it.
- `reference/firmware-project.md` is CardenzaHAL's `docs/FIRMWARE-PROJECT.md`: change the HAL's file, then
  `npm run rules` (`node tools/sync-rules.mjs`) here. CI reports when the copy is behind.
- `products/<device>/README.md`: one development guide per device, the same parts in each (the recommended way,
  toolchain and build, trying it on a device, publish, hardware reference, links). Only what is public: link to the
  source (a HAL's `pins.h`, a schematic) rather than copying it, and say plainly what is not public yet.
- Comments in `scripts/` cite sections of the community's specification (`COMMUNITY.md`) and the server's files.
  Those are not public; the community keeps them in step with this code.

## Before a commit

- `npm test` (Node 20 or later): the CLI against stand-in APIs and a demo Launcher on a pseudo-terminal (python3), the
  local checks, the documents, and a scan for secrets, private addresses and e-mail addresses.
- The community runs 203cli against its whole API in its own tests when it pins a commit; a change that needs a new
  API goes in after the community has it.
